Support email pipeline: approach and why it's reliable

The task: 50,000 support emails. Use an LLM to pull out the issue category, sentiment, urgency and any order ID, and return structured JSON that feeds a dashboard, so it must be reliable.

1. The pipeline

Read email→LLM fills 4 fields as JSON→Check the answer→Save row→Dashboard

Each email goes through the same steps. For 50,000 emails it runs as one batch job (half the price of one-by-one calls), and the dashboard reads the saved rows.

2. Why it's reliable

What could go wrongHow the pipeline stops it
LLM returns broken or messy JSONThe API is told the exact JSON shape, and every answer is checked before saving. A bad answer is never written.
LLM invents a value, e.g. category "complaint"Only a fixed list of values is allowed: 8 categories, 3 urgency levels, 3 sentiments.
LLM makes up an order IDThe ID is kept only if it actually appears in the email.
API error, timeout, rate limitAutomatic retries. Anything still failing goes to a "failed" file to re-run, so no email is lost.
Job stops halfwayIt resumes where it stopped and skips emails already done, so there are no duplicates.
An email says "ignore your instructions…"The email is treated as data to classify, never as instructions.
In one line: the dashboard never gets a bad row. Every answer is checked before it's saved, and no email is ever lost.

3. The core function

CATEGORIES = ["shipping", "refund", "billing", "product",
              "account", "technical", "travel", "general"]

def triage(email):
    answer = ask_llm(INSTRUCTIONS + email)       # LLM fills the 4 fields as JSON
    result = json.loads(answer)

    if result["category"] not in CATEGORIES:     # only allowed values
        raise ValueError("bad answer")           # -> retried, then saved as failed

    if result["order_id"] not in email:          # no made-up order IDs
        result["order_id"] = None

    return result                                # one clean row for the dashboard

In the real code the JSON shape is enforced by the API itself (structured output) and checked with Pydantic; the idea is the same.

4. Proof: I built it and ran it

To test on realistic data, I took real customer support messages from a public dataset (customers writing to 108 companies: Amazon, Apple, Uber, airlines, telecoms…) and turned 30,000 of them into emails: same message, plus a made-up name, subject and sometimes an order number.

  • 30,000 real support emails processed by the LLM (Claude Haiku): 30,000 valid rows, 0 failed.
  • Order IDs: I added a known order number to 10,401 of the emails, written different ways (ORD-123456, Order #123456, Ref: …). The pipeline found 100% of them, and 0 were made up: every ID it returned is in the email. It also picked up 309 references customers had written themselves, like booking codes and flight numbers.
  • Accuracy check: I labelled 200 of these real messages by hand. The LLM chose the same category as me 53% of the time. Many differences are fair two-way calls, like an iPhone bug: faulty product, or app problem?
